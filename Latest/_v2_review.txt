1. Introduction and Description
1.1 The system
SIFFT (Spark Ingestion Framework For Tables is an in-house, open-source Python library used on Driver and Vehicle Licensing Agency (DVLA) Data Platform that provides "a consistent interface for ingesting files into Apache Spark environments" [1]. It standardises what would otherwise be repetitive and fragile ingestion code: format-agnostic file reading with automatic delimiter and header detection, data-quality validation before load, consistent error handling across CSV/TSV/pipe/Excel files, and schema-evolution and merge/upsert support for Delta tables.
1.2 Use and function
A scheduled Databricks job drives SIFFT daily through three phases — Pull (SFTP → cloud volume), Ingest (volume → Delta via SIFFT), and Cleanup. Two configuration concepts govern each of the 50-plus daily feeds: how a file is *read* (delimiter, header, columns) and how its table is *written* (target table, format, mode, schema mode). SIFFT's modules map onto these:
`file_processing` (reading) 
`table_writing` (writing)
`dataframe_validation` (CSVW constraint checking)
`file_management` (safe move/list across local, S3, Azure and GCS)
1.3 Interactions with other systems
SIFFT does not run alone. It is invoked by Databricks notebooks/jobs, reads files delivered by SFTP into cloud storage (S3/Azure/GCS), writes to Delta tables in Unity Catalog, and the proposed improvement will read its configuration from a REST configuration service. The configuration service and SIFFT interact only indirectly, through the shared configuration the service owns and the job consumes.
1.4 Purpose within the business and criticality
These feeds populate curated Delta tables consumed across DVLA for Drivers, Vehicles and Lookups data. Because the pipeline runs daily and SIFFT validates data quality before data load, the correctness of its configuration is business-critical. A wrong delimiter or an invalid target table breaks that day's ingestion for a domain. Managing configuration safely and without a redeploy is therefore operationally significant, not merely convenient.
1.5 Intended end users
The direct users are the DVLA Data Platform team, who develop and operate SIFFT-driven jobs and author feed configuration. Indirectly, every downstream consumer of the ingested Delta tables depends on SIFFT behaving correctly.
1.6 Requirements (focused scope)
SIFFT (https://github.com/dvla/sifft) is a large library written in Python. In line with the brief this report focuses on the configuration and table-writing functionality including the `ReadConfig`/`WriteConfig` model, its services, the controlled vocabulary, and the write-behaviour selection that the improvement and the design patterns address.

3.1 Classes and responsibilities
`ReadConfigController` «RestController» — the HTTP entry point for read-configuration resources. Its sole responsibility is the web concern: mapping HTTP verbs to service calls and returning the correct status (201 + `Location` on create, 204 on delete, 200 otherwise). It holds no business logic. (The structurally identical `WriteConfigController` is omitted from the diagram to keep it at the required density, as noted in the diagram caption.)
`ReadConfigService` «Service» — the business-logic owner for read-configs. Responsibilities:
CRUD orchestration (`create`, `replace`, `delete`, `findAll`, `findById`), SIFFT-mirrored validation (single-character delimiter, header vocabulary, column identifiers, regex validity, referential integrity to a write-config), and the `test` operation that performs server-side processing of a sample line. It throws typed exceptions rather than returning error codes.
`WriteConfigService` «Service» — the business-logic owner for write-configs. Responsibilities:
CRUD orchestration and the write-specific validation — target-table identifier rule, vocabulary membership (format/mode/schemaMode) and the conditional merge rule (`merge` requires `mergeKeys` and `format = delta`).
`ReadConfigRepository` «interface» — persistence for read-configs. Extends Spring Data JPA's `JpaRepository`, inheriting CRUD, and declares two custom finders (`findByPattern`, `existsByPattern`) used for the uniqueness check. It contains no business logic.
`WriteConfigRepository` «interface» — persistence for write-configs; inherits CRUD from `JpaRepository` with no custom methods.
`ReadConfig` «entity» — the persistent representation of how an inbound file is read
(`pattern`, `delimiter`, `header`, `columns`, `maxCorruptPercent`, `writeConfigId`). 
It carries a full set of getters, setters and a no-arg constructor (JPA requirement) and owns its `columns`value-collection.
`WriteConfig` «entity» — the persistent representation of how a table is written
(`targetTable`, `format`, `mode`, `schemaMode`, `partitionBy`, `mergeKeys`, `addSourceMetadata`),
again with full accessors and a no-arg constructor, owning its partition/merge value-collections.
`ConfigVocabulary` «utility» — the controlled vocabulary (allowed delimiters, formats, modes, schema modes) held once as `static final` constants, with a private constructor to prevent instantiation. 4. Suggestion for Improvement or Extension
4.1 The change
The single significant change proposed is to externalise SIFFT's ingestion configuration from code into a managed service, and to make the write behaviour it selects pluggable. Today the configuration that tells SIFFT how to read each file and how to write each table is embedded in the consuming Databricks job as a hard-coded `FILE_MAPPINGS` list and `TableWriteOptions` objects. The improvement moves that configuration out of code so it can be created, changed and removed as data, and restructures the write path so a new table format is an added class rather than an edited conditional.
4.2 The existing problem and its likely cause
Problem. Any configuration change — onboarding a feed, correcting a delimiter, adding a table format — currently requires a code change and a redeploy of the Databricks Asset Bundle.
This is slow, requires developer and deployment access, and means a bad value is only discovered when the daily batch runs and fails, in production.
Likely cause. The configuration and the behaviour-selection logic are bound into the job at compile/deploy time. Two design characteristics cause this:
1. *Configuration-as-code.* The per-feed settings live in literals (`FILE_MAPPINGS`,`TableWriteOptions`) rather than in a store the system can read at run time. There is no boundary between "what to ingest" and "the program that ingests."
2. *Behaviour selected by conditionals.* Choosing how to write a table (by `format` or `mode`) is done with branching logic, so extending the set of formats means editing existing, tested code — the Open–Closed Principle is not satisfied on this axis.

The classes that *cause* the limitation are the ones that today hold literals and branch on them; the classes that must be *added or modified* to remove it are the services (construction and delegation) plus the proposed strategy hierarchy.
4.4 How the change addresses the limitation — relevant factors
- Maintainability. Onboarding a feed changes from "edit `FILE_MAPPINGS` + redeploy" to a single API call; decommissioning is a delete. The operational cost of a routine change falls from a release cycle to a request.
- Extensibility. With behaviour selected by a `FormatStrategy`, a new format is an added class and one registry entry — no edit to tested code (Open–Closed). This is the axis the Strategy pattern targets.
- Testability. Externalised, validated configuration and isolated strategies are unit-testable in isolation; the existing PoC already demonstrates this with 36 integration tests across all validation paths.
- Coupling and cohesion. The change separates "what to ingest" (data) from "how to ingest" (code), and gives each strategy a single responsibility — lowering coupling and raising cohesion compared with a job that holds both config and branching logic.
- Performance (honest note). The change is neutral-to-slightly-negative on raw performance (a config lookup and a strategy dispatch versus inlined literals), but the cost is negligible against a daily batch and is far outweighed by the maintainability and safety gains.
4.5 Evidence from the existing system
The change is appropriate because the existing system already points towards it: SIFFT is explicitly designed for extensibility — its documentation describes "custom format handlers, write modes, and constraint validators" and it ships a FormatHandler` family — yet the *configuration* that drives those handlers is not externally managed. The improvement closes that gap. The proof-of-concept `sifft-config-api` demonstrates the externalisation is feasible and safe (validation mirrors SIFFT's own rules, rejecting bad config at write time), which is direct evidence that the proposed change works rather than merely being plausible.
5. Design Patterns
5.1 What a design pattern is (framing)
A design pattern is a common, reusable solution to a problem that recurs in software design — "problem + solution in context" rather than finished code [GoF]. The idea was popularised by the *Gang of Four* (Gamma, Helm, Johnson and Vlissides) in *Design Patterns: Elements of Reusable Object-Oriented Software* [GoF], which catalogues patterns using C++/Smalltalk and OMT notation (OMT later evolved into UML).  The three principles that motivate the patterns used here, as covered in the module, are:
program to an interface, not an implementation; 
favour composition over inheritance;
use delegation.
5.1 Pattern 1 — Strategy
Purpose. Strategy lets you define a *family of algorithms*, put each in its own class behind a common interface, and make them interchangeable so the algorithm can be chosen and swapped at run time [GoF]. The object that uses the algorithm (the context) *delegates* to it rather than containing the algorithm itself.
The problem it addresses. In SIFFT, the way a table is written depends on its `format`(`delta`, `parquet`, `orc`). If this is handled with branching logic (`if format == "delta" …else if …`), then every new format means editing that same block of existing code — the classic problem the SimUDuck example showed with the `fly()` behaviour, where behaviour baked into a class becomes painful to change. The part that varies (the write algorithm) is tangled with the part that does not (the rest of the write process).
The solution / structure. Following the duck example, we take the part that varies and encapsulate it. A `FormatStrategy` interface declares a single operation, `write(...)`. Each format is a separate class that implements it — `DeltaStrategy`, `ParquetStrategy`, `OrcStrategy`— the direct equivalent of `FlyWithWings` / `FlyNoWay` implementing `FlyBehaviour`. The context, `WriteConfigService`, holds a `FormatStrategy` reference (a HAS-A relationship) and delegates the write to it via a `performWrite()`-style method, exactly as `Duck.performFly()` delegates to its `flyBehaviour`. The concrete strategy can be set through the constructor or a setter, so it can be changed at run time.
Figure 1. Strategy Pattern applied to SIIFT
Advantages.
- The write behaviours are encapsulated and reusable — the same strategy could be used elsewhere, just as the duck `FlyBehaviour` could.
- Behaviour can be changed at run time by swapping the strategy object.
- Uses composition and delegation (HAS-A) instead of inheritance (IS-A), which the lecture identified as more flexible.
- Adding a new format is a new class implementing the interface — the existing strategy classes and the context are untouched.
Disadvantages.
- More classes than a single conditional (one per behaviour), which the GoF note as the cost of the pattern.
- The context (or the calling code) still has to pick *which* strategy to use.
- Slight run-time overhead from delegation (the lecture's "black-box reuse" trade-off).
Why it is appropriate here. This is the same shape as the duck example applied to a real problem: SIFFT genuinely has a *family of algorithms* (how to write Delta vs Parquet vs ORC), and the externalised configuration (the improvement in Section 4) stores the `format`, so the stored value simply selects which strategy the context delegates to. It is a faithful, not forced, application of the one pattern taught so far.
### 5.2 Other candidate patterns *(provisional — based on prior exposure, not yet taught at university)*
The following two are not presented as final choices. Based on earlier exposure to design patterns outside the module, these look like promising options to compare against Strategy; I will confirm and develop them once they are taught officially (Decorator is scheduled next week;&gt; the remainder in later weeks). They are given here as high-level bullets only.
#### Candidate A — Decorator *(taught next week)*
- Why it might fit: the ingestion/write step has optional add-on responsibilities — e.g. attaching source-metadata, or deduplication/tracking — that could be *wrapped* around a core write behaviour instead of being hard-coded into it.
- Pros (high level): add responsibilities to an object dynamically without a subclass explosion; each add-on is a single-responsibility class; combinations are composed at run time.
- Cons (high level): can produce many small wrapper classes; the order of decorators can matter; the flow can be harder to follow than a single method.
- Status: to be confirmed after the Decorator lecture; the structure (component interface + concrete component + decorators) will be drawn then.
#### Candidate B — Observer *(scheduled for a later week)*
- Why it might fit: when an ingestion run completes, several things may need to react — recording tracking/confirmation, emitting metrics, notifying a dashboard — without the core process being coupled to each of them.
- Pros (high level): decouples the thing that changes state (the subject) from the things that react (observers); observers can be added/removed without changing the subject.
- Cons (high level): the flow of control is less explicit; observer ordering and lifecycle need care; can be harder to debug.
- Status: provisional, to be developed once taught; listed as the likely third comparison so the eventual evaluation can weigh behaviour-selection (Strategy) against event-reaction (Observer).
