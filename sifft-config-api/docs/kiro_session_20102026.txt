  The current end-to-end pipeline

  It's a library-call pipeline, not a service. The caller supplies a SparkSession and orchestrates four independent packages in sequence:

  process_file()  →  validate_csvw_constraints()  →  write_table()  →  confirm_processed() / safe_move()

  1. file_processing.process_file(file_path, spark, ...)
  - Optional dedup gate up front: if tracking is set, check_already_processed() short-circuits and returns success with 0 rows.
  - _validate_inputs() — requires a live SparkSession, checks file exists.
  - _select_handler() — dispatches by extension via a registry: Excel handler, delimited handler (CSV/TSV/pipe), or falls back to delimited parsing for
  unknown/no extension.
  - Returns a FileProcessingResult dataclass carrying dataframe, metadata (CSVW if found), rows_processed, rows_corrupt, checksum, and a tracking_context
  for deferred confirmation.
  - Dual error model: returns a result with .error dict, or raises FileProcessingException when raise_on_error=True.

  2. dataframe_validation.validate_csvw_constraints(df, metadata)
  - Runs only if result.metadata exists (CSVW *.csv-metadata.json alongside the file).
  - Returns CSVWConstraintReport with .valid and .violations. Separate from validate_schema()/apply_schema() which handle structural schema fixes.

  3. table_writing.write_table(df, table_name, spark, options)
  - validate_write_options() pre-flight, then dispatches through a mode handler registry: append / overwrite / merge / errorIfExists.
  - Formats via a format-handler registry (delta/parquet/orc). Merge uses DeltaTable.merge(...) and reads back operationMetrics for insert/update counts.
  - Returns TableWriteResult with row counts and duration_seconds.

  4. Post-write
  - confirm_processed(result, spark) — deferred tracking write, so a file is only marked done after the whole pipeline succeeds (nice design — see
  design_decisions/deferred-tracking.md).
  - file_management.safe_move() to move the file to a processed/quarantine location (local/S3/Azure/GCS via fsspec).

  Key architectural facts that matter for a web service:
  - Every entry point requires an active SparkSession passed in as an argument. The library never creates Spark.
  - No HTTP layer, no server, no async — it's synchronous, in-process library code.
  - Result objects already carry structured error dicts with to_dict() — these are essentially ready-to-serialize JSON payloads.
  - Batch helpers (process_files_batch, process_directory) loop synchronously.

  Where a Web Service fits — and what would need to change

  Here are the realistic options, with the design tensions each one hits.

  Option A — Thin REST/orchestration wrapper (recommended starting point) A FastAPI/Flask service exposing /process, /validate, /write, and a combined
  /pipeline endpoint. The service holds a long-lived SparkSession and calls the existing functions.
  - Fits well because: result objects already serialize cleanly via to_dict(); the dual error model maps naturally to HTTP status codes; the four packages
  are independent so you can expose them individually.
  - Changes needed: a session lifecycle manager (one shared Spark session, thread-safe access), request/response Pydantic schemas mirroring the dataclasses,
  and a decision on file transport (accept a path/URI vs. accept an upload then stage it to storage).
  - Tension: Spark is a shared, single-driver, blocking resource. Concurrent HTTP requests will contend for one session. You'd want a job queue rather than
  running Spark work inline in request threads.

  Option B — Async job API POST /jobs returns a job id immediately; a worker pool runs the pipeline; GET /jobs/{id} polls status. This matches Spark's
  blocking, long-running nature far better than synchronous REST.
  - Changes needed: a job store, worker/executor, and status model. duration_seconds and the result dataclasses give you most of the status payload already.

  Option C — Databricks-native service (Jobs API / Model Serving / DLT) Given this is explicitly Databricks/Unity Catalog targeted and already documents
  AutoLoader integration, the "web service" could be a Databricks Jobs REST trigger or a serving endpoint rather than a self-hosted Spark server. This
  avoids the "who owns the SparkSession" problem entirely because Databricks provides the cluster.

  Specific friction points to improve for any web-service exposure

  1. SparkSession ownership. Currently mandatory-injected. A service needs a module that owns/caches the session and guards concurrent use. This is the
  single biggest change.
  2. File input model. process_file takes a path. A service needs an upload-and-stage step (to S3/ADLS/DBFS) or must restrict to pre-staged URIs — plus
  path-traversal/validation guardrails since paths would come from HTTP clients (untrusted input).
  3. Blocking execution. All calls are synchronous and can be long. Needs a queue/async-job layer so HTTP workers aren't tied up.
  4. Serialization. FileProcessingResult.dataframe is a live Spark DataFrame — not serializable. The API must return metadata (row counts, checksum,
  violations) and write results, never the DataFrame itself. Decide what a response body contains.
  5. Auth & multi-tenancy. None today. A service needs authN/authZ, and storage_options (cloud credentials) must come from server-side secrets, not request
  bodies.
  6. Observability. It uses stdlib logging well, but a service needs request IDs, structured logs, and metrics around the already-tracked duration_seconds.
  7. Batch endpoints. process_files_batch/process_directory loop serially — a service should drive these through the job queue for parallelism.

  The core constraint everything revolves around

  SIFFT is a synchronous, in-process library where every Spark entry point needs an injected SparkSession, and the three registries (file handlers, write

  Option 1 — Thin synchronous REST facade (FastAPI)

  Expose the four packages as endpoints: POST /process, POST /validate, POST /write, POST /pipeline, plus POST /files/move, GET /files. The service holds
  one long-lived Spark session and calls the existing functions inline.

  - What it needs: a SparkSessionManager (singleton, lazy-init, lock-guarded), Pydantic request/response models mirroring the dataclasses, a mapping from
  the four exception types → HTTP status codes (the shared error_type field maps perfectly), and a rule that the DataFrame never crosses the wire —

  - Tension: Spark work runs in the request thread and blocks. Under concurrency, requests serialise on one driver. Fine for low-traffic/internal/demo use;

  - Best for: a reference service, internal tooling, or a proof of concept.

  The key semantic distinctions the course wants you to demonstrate — and justify in the report:

  idempotent (calling it twice leaves the same end state). That idempotency contrast is a classic exam/rubric point — make it explicitly in your
  justification.
  - PUT vs PATCH. PUT replaces the whole representation; PATCH does a partial update. You don't need PATCH, but mentioning you deliberately chose PUT (full
  replace) over PATCH (partial) is exactly the "defensible justification" the 10-mark section rewards.
  - DELETE is idempotent too — deleting an already-deleted config still leaves it absent (you return 404 the second time, but the state is unchanged). Worth
  a sentence.
  - Safe vs unsafe / idempotent matrix: GET = safe + idempotent; POST = unsafe + non-idempotent; PUT = unsafe + idempotent; DELETE = unsafe + idempotent.
  Putting this little table in your report is a cheap, high-value way to show method understanding.

  The key mental shift: they don't call each other — they share config

  The Java web service and the Python SIFFT code never talk to each other directly. There's no Java-calling-Python, no live connection. They are connected
  by one thing they both touch: the configuration data. The Java service writes config; the Databricks notebook reads config. That shared config is the
  entire integration point.

  Think of it like a settings file. One program edits the settings; another program reads the settings when it runs. They never meet — they just agree on
  where the settings live and what shape they're in.

  The complete loop, step by step

  1. A user updates config via the web service (Java). A member of the Data Platform team wants to onboard a new file type — say Customers.csv should load
  into drivers.curated.customers. Instead of editing notebook code and redeploying, they send an HTTP request:

  POST /api/v1/read-configs
  { "pattern": "Customers\\.csv", "delimiter": ",", "header": "auto",
    "columns": ["customer_id","name","age","status"], "writeConfigId": "..." }

  They'd do this through a simple admin UI, Postman, or a form — anything that speaks HTTP.

  2. The web service validates and stores it (Java). Your service checks the rules (single-char delimiter, valid table name, format in the allowed set,
  etc.) and — if valid — saves the config to a datastore. In your PoC that's the in-memory H2 database; in a real deployment it'd be a persistent database
  or a config table. The bad request is rejected here, immediately, with a 400/422. The config never reaches the pipeline in a broken state.

  3. The config sits in the shared store, waiting. Nothing runs yet. The config is just sitting there as data — the agreed source of truth for "how do we
  handle Customers.csv?"

  4. The scheduled Databricks job runs (Python/SIFFT). At 10:30 (the real schedule), the notebook job wakes up. Before processing files, it reads the
  current config from the shared store — instead of reading its hard-coded FILE_MAPPINGS list. So it now asks: "what's the latest config for the files I'm
  about to process?" and gets back the entry the user created in step 1.

  5. SIFFT does the actual work (Python). The notebook loops over landed files, and for each one uses the config it just read to drive SIFFT:

  mapping = get_config_for(filename)        # ← now comes from the shared store, not code
  result = process_file(path, spark,
               read_options={"delimiter": mapping.delimiter, "header": mapping.header})
  # apply columns, validate, then:
  write_table(result.dataframe, mapping.target_table, spark, write_options_from(mapping))
  confirm_processed(result, spark)

  SIFFT reads the file, validates it, and writes it to the Delta table.

  6. Data lands in the data store (D). The output arrives in Delta tables / Unity Catalog — the "D" box in the diagrams.

  So the loop is: user → web service → config store → (later) notebook reads config → SIFFT processes → Delta tables. The web service and SIFFT are joined
  only at the config store.
